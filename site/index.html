The problem

More reports can mean more use, not more risk.

Device makers and hospital systems watch adverse-event reports for early signs of a recall. But a heavily used device naturally creates more reports, so report count alone is an easy baseline to beat and a hard confound to ignore.

RecallRadar treats MAUDE as a noisy event signal and asks a narrow, testable question: can a small set of time-ordered features rank future Class I or II recalls better than volume alone?

MAUDE → feature row

One code. One quarter. One auditable score.

Report volume, injury share, death share, growth, manufacturer count, and prior recall history become a structured JSON record before the model sees them.

No key, no backend, no hidden prompt.

The output

A ranked list with a reason, not a black-box alarm.

A single LightGBM model ranks code-quarter rows. SHAP explains each recorded flag. The dashboard ships with precomputed results, so a recruiter can inspect the interaction in 30 seconds with no API key.

The system uses deterministic logic and regression testing around the model boundary. An LLM summarization layer could describe a result later, but it is not allowed to decide what gets flagged.

The pipeline

Every step has a check.

The project keeps the model small enough to explain and the evaluation strict enough to catch future leakage. The checks are code, not copy.

  1. Get the data

    Pull 40 quarters of MAUDE event counts and openFDA Class I or II recall records.

  2. Build the row

    Record adverse-event patterns plus prior recall count and time since last recall.

  3. Label the future

    Mark 1 when a recall starts in the next 12 months. An assertion proves every feature date and prior recall date ends first.

  4. Rank and explain

    Train LightGBM through 2021, validate on 2022, test on 2023 to 2024, and attach a SHAP reason.

  5. Compare honestly

    Report precision@50 and PR-AUC against report volume and prior recall count, with the model bootstrap interval.
